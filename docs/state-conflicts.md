# 상태 파일 충돌 보호

2026-09-22. 동일 로컬 경로의 동시 실행을 직렬화하고 Drive의 이미 발생한 콘텐츠 변경을 업로드 전에 검사한다. ATR 계산·시장 시간·알림 조건·PA 실행 창은 변경하지 않는다.

## 로컬 트랜잭션

`state_lock.state_transaction(path, timeout=30.0)`은 정규화한 절대 경로별 재진입 가능한 스레드 잠금과 OS 프로세스 잠금을 함께 사용한다. Windows는 `msvcrt.locking`, POSIX는 `fcntl.flock`이다. 다른 경로는 독립적으로 실행한다. 같은 스레드의 중첩 호출은 가장 바깥쪽 트랜잭션이 끝날 때까지 OS 잠금을 유지한다.

잠금 대상은 JSON 옆의 고정된 `<파일명>.lock`이다. JSON을 `os.replace`해도 잠금은 유지된다. 잠금 파일은 정상 종료·실패 후에도 삭제하지 않으며, 파일이 존재한다는 이유만으로 잠긴 것으로 판단하지 않는다. 프로세스가 종료되면 OS가 열린 잠금을 해제한다. PID나 파일 나이로 잠금을 훔치지 않는다. 잠금 파일을 수동으로 삭제하거나 교체해서는 안 된다.

상태 JSON 파일 자체가 심볼릭 링크인 경로는 고정 오류 코드로 거절한다. 링크 대상을 기준으로 잠근 뒤 원래 링크 경로를 원자적으로 교체하면 이후 호출의 잠금 파일이 달라질 수 있기 때문이다. 본문을 실행하거나 원본·링크를 바꾸기 전에 중단한다.

기본 대기 상한은 30초이며 잠금 획득 중 경합·경로·권한·I/O 오류 시 고정 코드의 `StateLockError`로 본문 실행 전에 중단한다. 해제 실패도 고정 오류로 전달하지만 이 경우에는 본문이 이미 실행됐을 수 있다. 다른 프로세스를 기다리는 동안에도 상태 JSON을 읽거나 수정하지 않는다. 지원되지 않는 플랫폼은 보호 없이 진행하지 않는다. 잠금 모듈을 import한 뒤 fork한 자식의 재사용은 거절하므로 별도 Python 프로세스로 시작한다.

보호 경계는 개별 파일 쓰기보다 넓다.

- Stop/포지션/알림/완료 창 API는 읽기→수정→원자적 저장 전체를 잠근다.
- 모니터 작업은 판단→알림 전송→상태 기록 전체를 잠근다. 로컬 데몬은 작업 단위로 잠그며 대기 중에는 보유하지 않는다.
- GHA는 상태 pull→선택한 작업→finally push 전체에서 같은 잠금을 유지한다. 최초 획득 실패 시 pull·작업·push를 시작하지 않는다.

모든 writer가 같은 경로와 잠금 규약을 사용하는 로컬 파일시스템을 대상으로 한다. 파일의 하드링크 별칭, 잠금을 무시하는 외부 편집기, 다른 체크아웃·호스트, 네트워크 파일시스템의 잠금 의미까지 보장하지 않는다. 외부 코드가 `load_all()` 결과를 오래 보관한 뒤 `save_all()`로 덮어쓰는 경우에는 그 전체 구간을 명시적으로 `state_transaction()`으로 감싸야 한다.

## Drive 업로드 사전 검사

검증을 통과한 pull 원본 바이트의 MD5를 기준값으로 보관한다. 변경이 없는 push 또는 로컬 파일이 없는 push는 기존처럼 업로드하지 않는다. 변경된 파일은 성공한 pull 기준값이 있어야 업로드할 수 있다.

업로드 직전 `files.get(fields="md5Checksum")`으로 원격 체크섬을 한 번 조회한다. 조회 실패·체크섬 누락/형식 오류·기준값과 불일치하면 원격 쓰기를 중단한다. 파일 ID, 체크섬, 원격 응답, 원래 예외는 오류 메시지에 넣지 않는다. 일치하면 검증된 로컬 바이트를 한 번 업로드하고, 응답 MD5까지 일치할 때만 새 기준값을 인정한다. 업로드 실패 또는 응답 불확실 시 기준값을 폐기하며 자동 재업로드하지 않는다. 다시 동기화하려면 새 pull이 필요하다.

**사전 검사는 원자적 compare-and-swap(CAS)이 아니다.** 검사 직후 다른 writer가 쓰고 그 뒤 이 실행이 업로드하면 변경이 유실될 수 있다(TOCTOU). 콘텐츠가 변경됐다가 같은 바이트로 돌아온 경우(ABA)와 메타데이터만의 변경도 MD5로 감지하지 못한다. 기존 GHA `concurrency: atr-monitor`는 계속 필요하다.

Drive v3의 `File.version`은 출력 전용이고 `files.update`에는 조건부 version 파라미터가 문서화되어 있지 않다. v2의 `File.etag` 제거가 HTTP ETag 헤더의 부재를 입증하는 것은 아니지만, `If-Match` 미디어 업로드의 서버 보장을 확인하지 못했으므로 이를 원자적 보호로 가정하지 않는다. 근거: [File](https://developers.google.com/workspace/drive/api/reference/rest/v3/files), [files.update](https://developers.google.com/workspace/drive/api/reference/rest/v3/files/update), [v2→v3 비교](https://developers.google.com/workspace/drive/api/guides/v2-to-v3-reference).

## 검증과 남은 범위

일반 회귀는 기존 `python scripts/run_offline_tests.py`에서 실행하며 외부 통신·자식 프로세스·운영 경로 접근 차단을 유지한다. `python -I -S -B -X utf8 scripts/run_state_lock_tests.py`는 별도 신뢰된 부모 실행기가 최소 코드 사본과 합성 상태를 준비한 뒤, 환경을 정리한 `-I -S -B` 자식만 실행한다. 자식은 제품 import 전에 I/O guard를 설치하며 추가 프로세스와 외부 통신을 차단한다. 실제 OS 경합·중첩 호출·원자적 교체 후 잠금 유지·정상 해제·강제 종료 해제·다중 writer 갱신 보존을 검사한다. CI의 잠금 검사는 Windows/Linux와 Python 3.11/3.12 조합에서 실행한다.

이 보호는 알림과 상태 저장을 하나의 원자적 거래로 만들지 않는다. 전송 성공 뒤 저장·업로드가 실패하면 다음 실행에서 알림이 반복될 수 있다. 로컬 CLI의 `--add-pos`/`--remove-pos`는 여전히 로컬 상태만 갱신하므로, 미동기화 변경이 다음 Drive pull에서 덮이는 순차 경로도 별도 R07이다. 다른 호스트 간 완전한 원격 충돌 방지, 원격 충돌의 자동 병합·재시도, 실제 Drive/Telegram 검증은 완료 범위에 포함하지 않는다.
